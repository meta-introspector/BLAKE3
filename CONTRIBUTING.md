# Working on BLAKE3 servil

This fork of BLAKE3 1.8.7, whose crate is `blake3-servil`, aims
at the fastest BLAKE3 in every situation a program meets: alone, beside
other work, beside other hashing threads, natively and in virtual
machines. This file holds what you need to change it and to cooperate
with its maintainers. Questions about BLAKE3 itself, or about the
official crate, belong upstream at
[BLAKE3-team/BLAKE3](https://github.com/BLAKE3-team/BLAKE3).

## Where things are

The README lists what the fork adds for callers; the code is laid out so:

- `c/`: the assembly kernels the crate builds. On AArch64, the integer +
  NEON hybrids (`blake3_neon_hybrid_aarch64.S`, generated by
  `tools/gen_neon_hybrid.py`) and the SME2 kernels; on x86-64, upstream's
  SSE4.1, AVX2, and AVX-512 kernels, and the fork's own: the pass of whole
  chunks with a partial one (`blake3_partial_x86-64_*`, generated by
  `tools/gen_x86.py`) and the chunk root in one call
  (`blake3_chunk_root_x86-64_unix.S`, generated by
  `tools/gen_x86_chunk_root.py`). Every kernel a user runs is assembly.
- `src/`: the Rust around them. `convenience.rs` and `performance.rs`
  (the two kinds of call, their contracts at the top), `incremental.rs`
  (the `Hasher`), `block.rs` (`Block` and `Batch`, the batch calls'
  input), `lib.rs` (what the calls share), `platform.rs` (detection and
  dispatch), `ffi_*.rs` (each kernel family's bindings), `pair.rs` (a whole chunk and a
  partial one side by side, x86-64), `many.rs` (batches), `each.rs`
  (collections, `update_each`), `lanes.rs` (the thread pool), `stream.rs`
  (the stream), `io.rs` (`update_reader`), `self_test.rs` (the startup
  self-test), `hasher.rs` (the Hasher's stack, loop, and chunk state),
  and `tree.rs` (the tree walk).
- `capi/`: the C API, `b3.h`, a thin layer over the crate
  (`capi/src/lib.rs`), tested from Rust against the official test vectors
  and from C and C++ on Unix (`capi/tests/`).
- `tools/verify/`: the proofs (docs/quality-manual.md, "Proofs"); `tools/mutants/`:
  mutation testing and the list of mutants known to survive.

Each part's design, the measurements behind it, and the ideas tried and
set aside sit in its own documentation: the module's, the generator's
header, the tool's README.

## Build and test

The supported C compilers are those of supported operating systems: GCC
12 or later (Debian 12's, the oldest; CI builds and tests with it) and
Clang as current releases ship it; official BLAKE3 serves older ones.

On AArch64 Linux and macOS the build includes the SME2 kernel when the C
compiler assembles SME2: Clang 17 or later (Xcode 15 or later), or GCC 14
or later with binutils 2.41. With an older compiler it builds without the
kernel and warns (`CC=clang-19 cargo build` adds it on Debian 12, for
example). On a
CPU with SME2, the check stops when the build lacks the kernel.

The tests run under [cargo-nextest](https://nexte.st), each in its own
process (`cargo test` stops at once and says so); the doc examples run
under `cargo test --doc`. The C API tests also need cargo-c
0.10.26+cargo-0.100.0 and `pkg-config` on `PATH`; see
[`capi/README.md`](capi/README.md) for installation.

```sh
cargo nextest run --release --lib --tests
cargo test --release --doc
cargo nextest run --release --manifest-path test_vectors/Cargo.toml
cargo nextest run --release --manifest-path capi/Cargo.toml   # the C API
sh tools/check-builds.sh            # the builds the suites leave out
RUSTFLAGS="--cfg shuttle" cargo test --release --test shuttle_finish --test shuttle_park   # the pool's handshakes, every schedule a model checker tries
python3 tools/mutants/check.py        # about an hour: every surviving mutant known, every time-out known
```

**While working, run the tests a change reaches:** `python3
tools/tests/reach.py check` compares the working tree with the last tree
it mapped and runs, through nextest, every test that ran a line the
change removes or rewrites, a test beside an insertion, a new test, and
every test when the change touches what line coverage cannot see (the
assembly, the build, the manifests, the nextest configuration, a
constant or a type or a `cfg`: anything the compiler, and no reading of
the text, decides the reach of). It prints each test's reason. A change
to a comment runs nothing; a change inside one function runs its tests,
a few seconds. `python3 tools/tests/test_reach.py` holds the rule's
controls, two of them Sam Shackleton's cases where a narrower rule hid a
failing test. `python3 tools/tests/reach.py map` records every test's
lines once (a minute); `check` keeps the map current from its own runs.
It replaces no suite above: the suites run before a landing; `reach`
makes the cycle between landings fast.

A change that makes a mutant survive, or lets a listed one be caught,
fails `tools/mutants/check.py`: add a test for the new survivor, or list
it in `tools/mutants/known-<arch>.txt` with the reason it survives (an
equivalent change, a choice between equally correct paths, another
machine's code; `--write` rewrites the list, each new row's reason
`UNCLASSIFIED` until you write one). A mutant whose tests the clock stops
(no test fails: a hang, or a wait that never ends) times out, an outcome
of its own, on `tools/mutants/timeouts-<arch>.txt` with its reason; the
check runs them every time, so one that a new test catches, or a change
in the code sets loose, is seen. A time-out is a bug the tests see only
by hanging: where a loop's variant or a wait's end can be asserted, make
it a failure instead (`CvStack::merge`, `update_turn`, `ensure_slow`
were made so), and the row goes.

A row whose reason claims speed alone ("speed", "equally correct
paths") is a claim a benchmark can test. `python3 tools/mutants/bench.py
[--since REV]` applies each surviving place alone and runs `bench-hashes
check` on it, about ten minutes a place. Slower: the path earns its
place. No cell runs it: a benchmark cell to write, or code to delete.
No cell slower, or faster: read it again at `--layouts 12`, then a
candidate to delete, or an improvement.

A survivor no test can kill is first a line to consider removing: an
unreachable branch goes (Task::run's batch branch did), and a pure
predicate gets a test of one thread even inside the pool (`visible`'s).
Where both paths are correct and one is faster, the reason says
`speed` and cites a measurement with the shortcut switched off
(`spare_lane`: 7935 B +29-53% without it). The handshake files
(`model files:` in the list: `finish.rs`, `park.rs`) are judged by
Shuttle's schedules as well as the suite, place by place: a mutant is
caught where either catches it. `check.py` narrows each mutant's tests
to those that ran its lines (`reach.py`'s map), gives each shard a
share of the CPUs, and caps each test process's memory, so a runaway
mutant cannot take the machine.

CI (`.github/workflows/ci.yml`) runs the suites on Linux x86-64 and arm64
(without SME2, and without SHA-3 under QEMU), and macOS's C API, for
every pull request, and by hand for a candidate that changes code for
those targets. A build for any other target (Windows, 32-bit,
big-endian, WebAssembly and the rest) stops with a message naming
official BLAKE3, which supports them, and
[#160](https://github.com/johnservil/BLAKE3/issues/160) holds what full
support takes (dedicated hardware of ours to benchmark, optimize and
test on, then the kernels and the gates). The Mac runner
(`tools/runner/`) runs the Rust suites natively. `sh tools/check-builds.sh`
runs, in minutes, the builds the suites above leave out: without std, on
one CPU without SME2, warnings as errors, and compile checks for x86-64.

The supported targets are 64-bit Arm (Linux, macOS) and x86-64 (Linux),
with the latest stable Rust (and any nightly feature the fork chooses to
use). Official BLAKE3 serves the rest.

The generated kernels are committed beside their generators. Edit the
generator, then run it: `python3 tools/gen_neon_hybrid.py >
c/blake3_neon_hybrid_aarch64.S`, `python3 tools/gen_sme2_hybrid.py >
c/blake3_sme2_hybrid_aarch64.S`, `python3 tools/gen_x86.py >
c/blake3_partial_x86-64_unix.S`, or `python3 tools/gen_x86_chunk_root.py >
c/blake3_chunk_root_x86-64_unix.S`;
`tools/check-builds.sh` fails when a file and its generator drift apart.

## Performance

Speed is the fork's purpose, so every change to `src/`, `c/`, `build.rs`,
`Cargo.toml`, or `Cargo.lock` passes a regression check first. The check
uses [bench-hashes](https://github.com/johnservil/bench-hashes), in a
checkout of its own beside this one (neither inside the other), named
with `--fork`. From this checkout's root:

```sh
git clone https://github.com/johnservil/bench-hashes ../bench-hashes
fork=$PWD
(cd ../bench-hashes && cargo run --release -- check --fork "$fork")                 # the working tree against HEAD
(cd ../bench-hashes && cargo run --release -- check --fork "$fork" --against OLD)   # a checkout at NEW
```

It builds the benchmark against both versions of the fork and runs them
alternately on the same machine, so it needs no stored numbers. Its
exit status:

- 0: no cell slower;
- 1: a regression, its cells listed;
- 2: no verdict, because other programs kept the machine busy during the
  check (run it again on a quiet machine).

`sh tools/install-git-hooks.sh` installs a pre-commit hook that runs it
for every commit that touches code. To run the full
benchmark against your working tree, see bench-hashes' `CONTRIBUTING.md`.

The check runs its pairs in two stages: four pairs over every cell the
change reaches, then sixteen fresh pairs over the cells it suspects,
judged among themselves. Planted at one input length, it caught +20%
and +10%, not +6%, which cells after a gap drown in (bench-hashes #66).
Where a short-message cell turns on where a stack or a buffer happens to
sit (4 KiB aliasing, bench-hashes #65), one build's layout can decide
its verdict; Sam Shackleton's `tools/offset_check.py` (BLAKE3 #141)
measures that.

One machine's verdict covers that machine. A change to the pool or to a
kernel faces the many-core x86 machine (the EPYC) and the Mac before it
lands: removing the owed wakes passed the i7 and made the EPYC 4-12%
slower in 14 pool cells (BLAKE3 #119), and the i7 then found its fix
16-25% slower.

A regression holds the commit: find its cause and fix it. When the
slowdown is the price of something worth more (correctness, a simpler
design), the maintainers decide; an accepted one lands with `--no-verify`
and its slowed cells, their numbers, and the decision in its message. A
streaming API's cells never slow to speed up another API. A commit in
`src/` or `c/` that leaves the machine code as it was (code for other
targets, tests, comments) skips the check with `--no-verify` and a line
in its message saying why. Commits made without the hook are checked
before they are pushed, each against its parent, and a run of them also
last against first, which sees slowdowns each step kept under the
margin.

## Branches and changes

`servil` is the main line. Work happens on `candidate/<topic>`
branches; a candidate joins `servil` as a fast-forward of its tip (so
what was checked is what lands) once:

- every suite above passes, and `sh tools/check-builds.sh`;
- CI passes on it, started by hand (`workflow_dispatch`) when it changes
  code for targets the VM and Mac do not run (x86-64, AArch64 without
  SME2);
- mutation testing passes on a change to the Rust
  (`python3 tools/mutants/check.py --since servil`: the mutants in the
  changed lines, and the ones the last map says a changed test catches);
- the regression check finds no slowdown on AArch64 Linux in a VM and
  natively on an Apple M4 Max. A candidate that changes no compiled code
  needs no speed check: it would compare identical code.

A change to a tool that runs for hours (`tools/mutants/check.py`,
`tools/verify/long-proofs.sh`, `bench-hashes regress` and `check`) lands
after a short run of it, start to finish, on each kind of machine that
runs it (the VM, the Mac, x86-64 Linux): a fault in its setup or
teardown otherwise costs a whole run, found at its end.

Jobs of hours run on `servil` overnight: the whole mutation run, and the
long proofs (`sh tools/verify/long-proofs.sh servil`, which posts the
commit's "long proofs" status). The proofs' inputs are the kernels
(`c/`), the specification (`c2sp/`), the proof tools (`tools/verify/`)
and the NEON generator; the script hashes them, and a commit whose
inputs match a run that passed (`tmp/long-proofs/inputs/`) gets its
status from that run in a second, so a change to the Rust, the build or
the pages never waits on the proofs. A failure there is fixed first, before the next change
to a kernel. After a candidate lands, bench-hashes pins its contender to
the new tip (`blake3-servil`'s `rev` in `Cargo.toml`, the full hash).
Its separate `clocks` pin fixes the instrument used on both sides of a
comparison. Pull requests are welcome against `servil`; say in yours
which machines you measured on.

## Releases

A release is a commit everyone can stand behind: every check the main
line runs once per change, run once more on that commit, and the pages
users read rewritten for it. `python3 tools/release-check.py [COMMIT]`
reads where each step left its result and prints PASS, FAIL, or OPEN
with the command that makes the evidence. The release's tracking issue
lists what it takes and ticks each step:

1. Once the code and API scope are settled, run `python3 tools/gen-ver.py
   X.Y.Z` from a clean release checkout. It stamps `X.Y.Z+<code parent's hash>`
   into the crate, CLI, C library/header and CHANGELOG, and makes a version
   commit and **local** tag. The version's hash names the code parent; the
   tag names the version commit. cargo-c derives pkg-config's version from
   the C crate; the tool prints the release's exact dependency line. Keep
   the tag unpublished while validating that commit; a branch at it makes
   it available to CI. Evidence is named by this version commit.
2. CI, every job, dispatched with `workflow_dispatch` on the exact candidate;
   `sh tools/check-builds.sh`. Pull-request CI normally checks a synthetic
   merge, so its head-SHA label alone is not evidence for the release commit.
3. `bench-hashes check --against <previous release tag> --cells all`, on
   the VM and the Mac: each commit was checked against its parent alone,
   and this sees what small slowdowns add up to. When the old side
   predates the bench's calls, `--old-bench <bench commit>` builds it with
   a bench that calls it the same way (the runner's "old_bench_commit").
   That bench must build beside the fork, as every bench from 1f4dfd63 on
   does; one from before the two became separate checkouts (0.18.3 and
   older) builds only inside it, and `check` says so.
4. The long proofs, every kernel; the full mutation run.
5. A paired package dry-run (below). The CLI needs the new library version,
   which is not on crates.io yet; checking it alone cannot validate the pair.
6. The pages, read as a newcomer would: the README's servil preface,
   `QUALITY.md` and `docs/quality-manual.md`, `CHANGELOG.md` (what
   changed for users, in their terms), the supported-platforms table
   (exactly what CI runs).
7. A full bench-hashes run on the version commit on the Mac, its results
   retained for publication with the release and named on the map.
8. Once the gates and human reviews accept that exact version commit,
   publish its tag and artifacts:
   - the crates: publish the pair from the same staged checkout and lock
     used for the dry-run, with `--locked` and the same explicit `-p` names.
     Cargo publishes the dependency first. The CLI package is `b3sums`
     (crates.io's `b3sum` is official BLAKE3's);
   - b3sum's binaries, built from a clean tree at the tag on each machine
     by `sh tools/b3sum-release.sh` (statically linked on Linux), each
     with its `.sha256` and `.b3`;
   - the C library, staged by `cargo cinstall --release --destdir=STAGE`
     in `capi/`: the static and shared libraries, `b3.h`, and the
     pkg-config file (`capi/README.md`);
   - the GitHub release, its text the CHANGELOG entry.
9. The eBASH submission, pinned to the tag (`supercop/README.md`).

### Paired package dry-run, before either crate is published

From the version-stamped checkout, with no tracked changes, use Cargo's
multi-package support in a temporary parent workspace. The staged clone
is clean; the candidate's manifests and Git tree stay unchanged. Select
the two packages explicitly, so other path dependencies in the tree are
not publication targets:

```sh
(
set -eu
git diff --quiet HEAD
commit=$(git rev-parse HEAD)
stage=$(mktemp -d)
git clone --shared --no-checkout . "$stage/checkout"
git -C "$stage/checkout" checkout --detach "$commit"
printf '[workspace]\nmembers = ["checkout", "checkout/b3sum"]\nresolver = "3"\n' > "$stage/Cargo.toml"
cargo publish --dry-run --manifest-path "$stage/Cargo.toml" \
    --target-dir "$stage/target" -p blake3-servil -p b3sums
echo "Retain paired-package workspace: $stage"
)
```

Cargo stages the unpublished library while verifying the CLI. Retain the
workspace lock, logs and archives, with both artifact digests. The CLI's
packaged lock must name the checksum of that exact library archive.
Append `publish-dry-run: ok` to the commit-named release log only when the
paired command succeeds; this is a dry-run, never permission to upload.
The final publication uses the same source and locked dependency resolution.
